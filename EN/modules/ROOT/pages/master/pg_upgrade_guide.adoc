= Upgrading from PostgreSQL to IvorySQL

== Overview

IvorySQL is built on the latest PostgreSQL kernel and adds Oracle compatibility on top of it. If you are already running PostgreSQL, this guide helps you upgrade your data to IvorySQL smoothly and enable Oracle-compatible mode as needed.

This guide describes three upgrade paths and provides pre/post-migration checklists:

[cols="2,2,3,2"]
|===
|Path |Use case |Advantages |Limitations

|pg_dump / pg_restore logical migration
|Cross-version, cross-platform migration with small to medium data volumes
|Safest, best compatibility, supports large version gaps
|Downtime depends on export/import duration

|pg_dumpall full-cluster migration
|Moving an entire instance (including global objects) at once
|Preserves roles, tablespaces, and other global objects
|Also requires a downtime window

|Logical replication
|Online migration with minimal downtime
|Source stays available; switch at any time
|Requires PostgreSQL 10+, more complex configuration
|===

[IMPORTANT]
Do not use `pg_upgrade` to upgrade directly from vanilla PostgreSQL to IvorySQL. IvorySQL adds Oracle-compatibility objects and configuration inside the kernel, and `pg_upgrade` cannot guarantee that these compatibility components are initialized correctly in the system catalogs. Use the logical migration or logical replication paths described in this guide.

== Pre-upgrade preparation

=== Confirm IvorySQL and PostgreSQL versions

IvorySQL 5.x is based on PostgreSQL 18. Confirm both versions:

[source,shell]
----
# Source PostgreSQL
psql -U postgres -c "SELECT version();"

# Target IvorySQL
psql -U postgres -p 5432 -c "SELECT version();"
----

=== Install IvorySQL

Install IvorySQL by following the xref:master/installation_guide.adoc[installation guide]. When initializing the instance, choose the compatibility mode and case-insensitive (CI) options according to your business needs:

[source,shell]
----
/usr/local/ivorysql/ivorysql-5/bin/initdb -D /data/ivorysql -U postgres
----

After initialization, check the key parameters in `ivorysql.conf`:

[source,ini]
----
ivorysql.compatible_mode = oracle
ivorysql.port = 1521
port = 5432
----

IvorySQL listens on both the PostgreSQL-mode port (5432) and the Oracle-compatible-mode port (1521) by default. During the upgrade you can verify PostgreSQL behavior through port 5432 first, then switch to port 1521 to use Oracle compatibility features.

=== Source-side checklist

* Record the source version, `encoding`, and `lc_collate`/`lc_ctype`, and keep them consistent when running initdb on the target.
* Rehearse table creation in advance with `pg_dump --schema-only` and flag any objects that require Oracle compatibility features.
* Check whether your data relies on the difference between empty strings and `NULL`: in PostgreSQL, `''` and `NULL` are distinct, while IvorySQL's Oracle-compatible mode follows Oracle semantics and treats empty strings as `NULL`. Query results that depend on this semantic change and need business-side evaluation.
* Capture row counts of large tables as the baseline for post-migration validation.

== Path 1: pg_dump / pg_restore logical migration

=== Export the source database

Dump the database on the source PostgreSQL (prefer a `pg_dump` of the same major version as the source):

[source,shell]
----
pg_dump -U postgres -Fc -d appdb -f appdb.dump
----

Use the `-N`/`-n` and `-T`/`-t` options to exclude specific schemas or tables.

=== Restore into IvorySQL

Restore the dump into the IvorySQL instance (via port 5432 to keep PostgreSQL behavior):

[source,shell]
----
# Create the target database first
psql -U postgres -p 5432 -c "CREATE DATABASE appdb;"

# Restore the data
pg_restore -U postgres -p 5432 -d appdb --no-owner --no-privileges appdb.dump
----

`--no-owner` and `--no-privileges` skip source-side ownership and grants. If you recreated the same roles on the target, you can drop these options.

=== Migrate global objects

`pg_dump` does not include roles or tablespaces. For a fresh target instance, migrate global objects separately:

[source,shell]
----
# Export globals from the source
pg_dumpall -U postgres --globals-only -f globals.sql

# Import on the target (edit out superusers and pre-existing objects first)
psql -U postgres -p 5432 -f globals.sql
----

== Path 2: pg_dumpall full-cluster migration

If the source instance is small, or you want to move global objects together with the data, use `pg_dumpall` directly:

[source,shell]
----
# Full-cluster export as plain SQL
pg_dumpall -U postgres -f full_cluster.sql

# Import on the target
psql -U postgres -p 5432 -f full_cluster.sql
----

[NOTE]
`pg_dumpall` produces plain-text SQL and does not support parallel restore. Prefer Path 1 for large instances.

== Path 3: logical replication online migration

For businesses that cannot tolerate long downtime, use logical replication to keep the source and IvorySQL in sync, then cut over within a short window.

=== Configure the source

Adjust `postgresql.conf` on the source PostgreSQL and restart:

[source,ini]
----
wal_level = logical
max_replication_slots = 10
max_wal_senders = 10
----

Make sure `pg_hba.conf` allows the IvorySQL host to connect for replication.

=== Pre-create the structure on the target

Create the same table structures on IvorySQL in advance (you can generate them with `pg_dump --schema-only`) and ensure the target tables have a replica identity:

[source,sql]
----
-- Tables with primary keys need no extra step
-- Tables without primary keys require a replica identity
ALTER TABLE app_table REPLICA IDENTITY FULL;
----

=== Create publication and subscription

[source,sql]
----
-- Create a publication on the source
CREATE PUBLICATION app_pub FOR ALL TABLES;

-- Create a subscription on IvorySQL
CREATE SUBSCRIPTION app_sub
  CONNECTION 'host=src_host port=5432 dbname=appdb user=replica password=***'
  PUBLICATION app_pub;
----

After the subscription is created, IvorySQL performs the initial sync and then continuously applies incremental changes.

=== Cutover

1. Stop writes on the source and wait until the subscription lag reaches zero (check `pg_stat_subscription` for `latest_end_lsn`).
2. Disable the subscription on IvorySQL: `ALTER SUBSCRIPTION app_sub DISABLE;`
3. Point the application connection string to IvorySQL, using port 1521 if Oracle-compatible behavior is desired.
4. After a stability observation period, drop the subscription and decommission the source.

== Post-upgrade validation

=== Basic checks

[source,sql]
----
-- Compare row counts of key tables (run on both source and target)
SELECT count(*) FROM app_table;

-- Check sequence values to avoid primary-key conflicts after cutover
SELECT last_value FROM app_id_seq;
----

Logical replication does not replicate sequence values. Synchronize sequences manually before cutover:

[source,shell]
----
# Export sequence state from the source
psql -U postgres -d appdb -Atc \
  "SELECT 'SELECT setval(' || quote_literal(quote_ident(sequencename)) || ',' || last_value || ');' \
   FROM pg_sequences WHERE schemaname = 'public'" > sync_sequences.sql

# Execute on IvorySQL
psql -U postgres -p 5432 -d appdb -f sync_sequences.sql
----

=== Enable Oracle-compatible mode

After validation, connect through port 1521 and verify Oracle-compatible behavior:

[source,sql]
----
-- Confirm the compatibility mode
SHOW ivorysql.compatible_mode;

-- Verify Oracle-style objects
SELECT SYSDATE FROM DUAL;
SELECT NVL(NULL, 'N/A') FROM DUAL;
----

== FAQ

* **Empty-string semantics**: in Oracle-compatible mode `''` equals `NULL`. If your business depends on the PostgreSQL distinction between empty strings and NULL, adjust the related queries or data.
* **Identifier casing**: Oracle-compatible mode follows Oracle's case-folding rules; unquoted identifiers are treated as uppercase. Lowercase object names migrated from PostgreSQL remain accessible with double quotes, but review naming conventions before switching.
* **Extension compatibility**: confirm that PostgreSQL extensions used on the source are adapted for IvorySQL. See the xref:master/ecosystem_components/ecosystem_overview.adoc[ecosystem component list].
* **Ownership**: after restoring with `--no-owner`, objects belong to the user who ran the restore. Create the roles on the target in advance to preserve the original permission model.
